# @ft/api

[English](README.md) · **Русский**

Сервис на NestJS: принимает UDP-телеметрию игры, транслирует её в дашборды по WebSocket, определяет сессии и круги, сохраняет их в PostgreSQL и отдаёт историю по REST.

```sh
pnpm --filter @ft/api db:local    # PostgreSQL без Docker, см. раздел «База данных»
pnpm --filter @ft/api db:migrate  # применить миграции к DATABASE_URL
pnpm --filter @ft/api dev         # режим watch, читает apps/api/.env, если он есть
pnpm replay <запись> --loop       # во втором терминале, если игра не запущена
```

## Конфигурация

Переменные окружения проверяются один раз при старте; некорректное значение останавливает процесс с сообщением, в котором названа переменная. Обязательна только `DATABASE_URL`, см. [`.env.example`](.env.example).

| Переменная             | По умолчанию  | Значение                                                                                            |
| ---------------------- | ------------- | --------------------------------------------------------------------------------------------------- |
| `HTTP_HOST`            | `0.0.0.0`     | Адрес HTTP и WebSocket; все интерфейсы, чтобы мог подключиться телефон в локальной сети             |
| `HTTP_PORT`            | `4000`        | Порт HTTP и WebSocket                                                                               |
| `UDP_HOST`             | `127.0.0.1`   | Адрес приёма телеметрии; `0.0.0.0` — если игра на другом компьютере или Xbox                        |
| `UDP_PORT`             | `9876`        | Порт приёма телеметрии; 5200–5300 отклоняются, их занимает игра                                     |
| `TELEMETRY_SOURCE`     | `udp`         | `udp` слушает игру; `replay` вместо этого проигрывает `REPLAY_FILE` по кругу, для демо на сервере   |
| `REPLAY_FILE`          | —             | Запись для повтора (их делает `pnpm record`)                                                        |
| `RECORD_SESSIONS`      | `true`        | Сохранять сессии и круги; в режиме повтора выключается, иначе одна сессия повторялась бы бесконечно |
| `LIVE_RATE_HZ`         | `30`          | Кадров в секунду для live-клиентов                                                                  |
| `TELEMETRY_TIMEOUT_MS` | `2000`        | Тишина, после которой игра считается отключённой                                                    |
| `DATABASE_URL`         | обязательна   | URL `postgresql://` базы истории                                                                    |
| `DATABASE_POOL_SIZE`   | `10`          | Соединений с базой; 1 для PGlite, который выполняет одну сессию за раз                              |
| `LOG_LEVEL`            | `info`        | `fatal` … `trace` или `silent`                                                                      |
| `LOG_PRETTY`           | в development | Читаемые логи вместо JSON                                                                           |

### Где запущена игра

- **Тот же ПК, Steam:** подходят значения по умолчанию; Data Out направить на `127.0.0.1:9876`.
- **Тот же ПК, Microsoft Store или PC Game Pass:** Windows не даёт игре отправлять пакеты на loopback, пока для неё не добавлено исключение, см. [настройку сети](../../docs/fh6-data-out.ru.md#настройка-сети-в-windows).
- **Другой ПК или Xbox:** задать `UDP_HOST=0.0.0.0`, разрешить UDP-порт в брандмауэре и направить Data Out на LAN-адрес этой машины.

## Интерфейс

| Точка входа                       | Назначение                                                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /health`                     | Проверка живости плюс состояние телеметрии и счётчики пакетов. Отключённая игра не делает сервис нездоровым.                               |
| `WS /live`                        | Поток от сервера: `hello` при подключении, `status` при каждой смене состояния, `frame` не чаще `LIVE_RATE_HZ` раз в секунду во время езды |
| `GET /sessions?cursor&limit&kind` | Сессии, новые первыми, страницами по `limit` (по умолчанию 20, не больше 100); `nextCursor` получает следующую страницу                    |
| `GET /sessions/:id`               | Сессия с её кругами                                                                                                                        |
| `GET /laps/:id`                   | Круг с трассой: скорость, педали, передача, перегрузки и положение на маршруте. Кешируется навсегда: записанный круг не меняется           |

Схемы сообщений и ответов лежат в [`@ft/contracts`](../../packages/contracts/README.ru.md). Почему поток устроен именно так: [ADR 0003](../../docs/adr/0003-live-websocket-stream.ru.md); API истории: [ADR 0006](../../docs/adr/0006-history-rest-api.ru.md).

## Сессии и круги

Чистый трекер в [`src/sessions/domain`](src/sessions/domain) превращает поток пакетов в сессии и круги, следуя тому, что игра присылает на самом деле ([жизненный цикл гонки](../../docs/fh6-data-out.ru.md#жизненный-цикл-гонки)):

- Сессия — непрерывная езда на одной машине. Гонка и свободная езда вокруг неё — разные сессии; новая машина, новая гонка или две минуты без езды начинают новую.
- Круг завершается, когда увеличивается счётчик кругов игры, со временем круга от самой игры. Время последнего круга гонки игра не сообщает, поэтому оно берётся из часов круга, когда езда не возобновилась за 30 с.
- Перемотка обрезает круг до места, откуда продолжилась езда, и отменяет круг, если откатывает назад через линию.
- Сессии без завершённого круга, в которых проехано меньше 10 с или 100 м, например показ машины перед гонкой, отбрасываются.
- У каждого круга хранится трасса с передискретизацией вдоль маршрута, поэтому два круга одного маршрута совмещаются точка в точку.

Хранятся только эти производные записи, поток пакетов — никогда: [ADR 0005](../../docs/adr/0005-session-storage.ru.md).

## База данных

PostgreSQL через Prisma 7. Схема — [`prisma/schema.prisma`](prisma/schema.prisma), миграции из [`prisma/migrations`](prisma/migrations) применяются командой `pnpm --filter @ft/api db:migrate`. Клиент генерируется в `src/generated` задачей `generate`, которую Turborepo запускает перед build, typecheck, lint и test.

`pnpm --filter @ft/api db:local` поднимает встроенный PostgreSQL (PGlite) по адресу из `.env.example` с данными в `apps/api/.pglite`, так что для разработки Docker не нужен. `pnpm --filter @ft/api db:import <запись>` добавляет запись в историю так, будто заезд прошёл в момент записи; демо на сервере так показывает в истории тот же заезд, что крутит вживую. Команда запускается из собранного кода и пропускает запись, если за её интервал в истории уже есть сессии.

Новая миграция пишется через `prisma migrate dev --create-only`; ей нужна вторая пустая база в `SHADOW_DATABASE_URL`.

## Структура

```
src/
  config/      схема окружения и типизированный провайдер конфигурации
  telemetry/   UDP-источник, декодирование, состояние подключения (offline / idle / driving)
  live/        WebSocket-шлюз, сборка кадров, прореживание, работа с медленными клиентами
  sessions/    определение сессий и кругов (domain/), запись в базу, REST-контроллер
  database/    жизненный цикл клиента Prisma
  health/      проверка здоровья
prisma/        схема и миграции
scripts/       локальная встроенная база
```

Источник телеметрии скрыт за интерфейсом, поэтому демо-режим может подать в тот же пайплайн запись.

## Тесты

- Модульные тесты покрывают валидацию конфигурации, автомат состояний (марбл-тесты RxJS), сборку кадров, прореживание и рассылку.
- [`live.e2e.test.ts`](test/live.e2e.test.ts) запускает настоящее приложение на свободных портах, проигрывает в него по UDP 8-секундную запись из игры и сверяет каждое сообщение WebSocket с контрактом, а также проверяет частоту кадров, смену состояний и health-check.
- Трекер сессий проверяется на симуляции игры (круги, последний круг, перемотка через линию, рестарт, смена машины) и на записанной кольцевой гонке в два круга, времена которых должны совпасть с показанными в игре.
- Тесты базы работают на PGlite внутри процесса со схемой из закоммиченных миграций; отдельный тест проверяет, что миграции дают в точности схему Prisma. Ни сервер базы данных, ни Docker не нужны.
- [`sessions.e2e.test.ts`](test/sessions.e2e.test.ts) подаёт записанную гонку в приложение с исходными метками времени и читает сессию, её круги и трассу обратно по HTTP.

Vitest компилирует код через SWC, потому что Nest нужны метаданные декораторов, которых нет в стандартной трансформации Vite.
