# 0008. Хостинг: один VPS за его собственным nginx, проигрываемый заезд, образы из CI

[English](0008-hosting-on-a-vps.md) · **Русский**

- Статус: принято
- Дата: 2026-10-03

## Контекст

Проекту нужно публичное демо, которое работает в любое время, даже когда в игру никто не играет. У частей проекта разные потребности:

- **API** нужны PostgreSQL и долгоживущие WebSocket-соединения.
- **Live-поток** приходит из игры по UDP в домашней сети игрока. Публичный сервер его никогда не получает.
- **Страница демо** проигрывает видео геймплея размером около 130 МБ.

Многие из тех, кто откроет демо, находятся в России, где домены Vercel открываются ненадёжно.

У автора уже есть небольшой VPS: 2 CPU, 4 ГБ памяти, диск 30 ГБ. Его nginx уже обслуживает другой сайт на портах 80 и 443. На том же хосте работают и другие сервисы, один из них в Docker-контейнере. Всё добавляемое не должно ничего из этого менять.

## Решение

- **Всё работает на VPS в Docker Compose:**
  - PostgreSQL;
  - разовый контейнер `migrate`;
  - API;
  - сервер Next.js.

  Контейнеры публикуют порты только на `127.0.0.1`.

- **Точка входа — nginx хоста.** Ещё один файл конфигурации даёт стеку два домена, проксирует WebSocket `/live` и отдаёт медиа демо с диска. Имя файла выбрано так, чтобы он шёл последним: существующий сайт остаётся сервером по умолчанию на порту 443.
- **TLS выпускает certbot в режиме webroot.** Один сертификат покрывает оба имени, а хук перезагрузки хранится в его собственных настройках продления. certbot никогда не правит конфигурацию nginx.
- **API проигрывает записанный заезд.** Заезд идёт по кругу как live-поток (`TELEMETRY_SOURCE=replay`), с исходными интервалами. Live-поток сообщает, что его источник — запись, и дашборды это показывают. В этом режиме ничего не записывается (`RECORD_SESSIONS=false`). Вместо этого `migrate` один раз импортирует тот же заезд в историю. Импорт пропускается, если этот отрезок времени уже покрыт сессиями.
- **CI собирает образы и публикует их в GHCR.** Сервер их только скачивает:
  - образы публичные;
  - у них теги `latest` и SHA коммита;
  - они подходят для любого домена: контейнер web берёт публичный адрес API во время работы.
- **Видео демо лежит на диске сервера**, рядом со своей дорожкой телеметрии. Его нет ни в git, ни в образах. Оно закодировано в AV1, с копией в H.264 для браузеров без AV1. Дорожка отдаётся заранее сжатой.
- **Диск защищён.** Лог каждого контейнера ограничен 3 × 10 МБ через драйвер Docker `local`, без изменения собственных настроек Docker. Эти сайты не ведут журнал доступа, а старые образы удаляются после обновления.

## Последствия

- **Одна машина — единая точка отказа.** Для демо это приемлемо. База хранит только импортированный заезд, который `migrate` создаёт заново, поэтому бэкапы не нужны.
- **Деплой — ручной `docker compose pull && docker compose up -d`.** Ключ от сервера не хранится в CI. Для демо, которое меняется время от времени, такой обмен оправдан.
- **Сайты работают по HTTP/1.1.** С nginx 1.18 на хосте `http2` в строке listen включился бы на весь порт, включая существующий сайт.
- **Видео приходится готовить и загружать вручную.** В [docs/deploy.ru.md](../deploy.ru.md) есть команды: нарезка клипа, сдвиг между видео и телеметрией, экспорт дорожки.
- **Шаги записаны** в [docs/deploy.ru.md](../deploy.ru.md), а конфиг nginx хранится в [deploy/nginx](../../deploy/nginx/forza-telemetry.conf).

## Рассмотренные альтернативы

- **Vercel для веб-приложения, VPS для API.** Это дало бы CDN и превью-деплои бесплатно. Но WebSocket API всё равно должен жить на VPS, доступность Vercel из России под вопросом, и демо оказалось бы разделено между двумя платформами.
- **Caddy или Traefik в compose-стеке ради автоматического TLS.** Обоим нужны порты 80 и 443, которые занимает nginx хоста. За этим nginx любой из них лишь добавил бы лишний переход.
- **Сборка образов на сервере.** Для неё на диске 30 ГБ нужны весь инструментарий и кэш сборки, а на 2 CPU сборка медленная. CI и так собирает образы для каждого коммита.
- **Деплой из CI по SSH.** Деплой стал бы автоматическим, но GitHub хранил бы ключ от сервера, на котором работают и другие сервисы.
- **Видео в репозитории (Git LFS) или в образе web.** Любой вариант сделал бы каждый clone или pull на сотни мегабайт тяжелее, а видео меняется по своему графику, а не вместе с кодом.
- **Live-демо от рекордера на ПК.** Показывало бы настоящую езду, но демо зависело бы от того, включён ли этот ПК.
